# 推送架构 —— 观察驱动（谁在看才推谁）

> 状态：**阶段①②已实现，③④待做**。上位：`docs/20260914/game.md`。
>
> 一句话：**不推全量。渲染状态没变的不推；不看的详情不推；几乎不变化的只推一次。**

---

## 0. 为什么必须改（实测）

108 人的场景，`PUSH_HZ = 60`、快照全量：

```text
day 1 = 100 KB / 帧      day 2 = 120 KB      day 3 = 141 KB
其中 events 41 KB · memory 34 KB · signals 9 KB · intent 9 KB · plan 7 KB
真正每帧需要的渲染字段 (position/loc/travel) ≈ 3 KB
```

**60 Hz × 141 KB = 8.5 MB/s** → 客户端解析跟不上 → TCP 回压 →
服务端 `send_text` 超时（1.5 s）→ **判为卡死并断开** → 客户端重连 → **无限重连**。

而**暂停时也在 60 Hz 全量重发**。

---

## 1. 根本原因：把三种东西用同一种频率发

| 数据 | 变化频率 | 真正需要它的范围 |
|---|---|---|
| `position` / `travel.waypoints` | **只在状态迁移时** | **视口内** |
| `activity` / `act_class` | 偶尔 | 视口内 |
| `signals`（energy/hunger/…） | 每 tick | **只有选中的那一个** |
| `memory` / `events` / `intent` / `plan` | 偶尔 | **只有选中的那一个** |
| `locations` / `map` / `canvas` | **几乎不变** | 一次即可 |

---

## 2. 目标架构：三层

```text
L1 渲染层   每帧(≤20Hz)且【状态变了】才推   视口内 NPC 最小集 + 物品
L2 详情层   每帧只推【选中的那个】            signals/memory/events/intent/plan
L3 静态层   变化时才推                       locations / map / canvas
```

### 三个必须一起成立的规则

1. **位置只在状态迁移时推**（下节）
2. **正在被看的每帧全量推**（否则进度条不动 —— 见 §2.1）
3. **消失的 id 要显式告知**（合并式更新的代价 —— 见 §2.2）

### 2.1 观察集：进度条为什么必须靠"被看见"

`signals`（进度条 / 生命条）**每 tick 都在变，但不属于渲染签名** ——
若把它算进签名，所有人每帧都脏，优化作废。

```
症状: 站着不动的 NPC 的进度条永远停住
根因: 不下发 → 客户端那份 signals 冻在旧值
修法: 【观察集】—— 客户端上报"我在看谁 / 看哪栋楼", 这些每帧全量下发
```

客户端在选中变化时发 `select {npc, location}`；后端 `_watched()` 返回
{选中的那个} ∪ {选中建筑里的人（含各层单元，上限 64）}，并入 dirty 集合。

### 2.2 消失的 id：合并式更新的代价

客户端是**合并**而不是替换 —— 代价是**它永远不知道谁没了**。

```
症状: NPC 死了 / 物品被吃了, 客户端还留着一个幽灵
修法: 快照带 gone: {"npcs": [...], "entities": [...]}
      = 上帧之后从世界消失的 id（空时不占位）
```

另有一条**事件路径**：`npc_died` 走事件流 → 客户端 `Store.apply_event()`
立刻删除。（事件与快照同帧，先到先做，删除是幂等的。）

> 注意: 驼鸟式“反正下一帧会补”在这里不成立 —— 合并式更新必须配墓碑。

### 核心规则：**位置只在状态迁移时推**

```text
渲染签名 = (所在地点, 当前活动, 是否在途(目的地, 出发刻, 到达刻))
→ 签名没变 → 【整条 NPC 不下发】

在家不动的 NPC  → 签名恒定  → 永远不推位置  ✅
路上的 NPC      → 出发时推一次 waypoints
                 途中一帧都不推(客户端自己沿折线插值)
                 到站时推一次(清掉 travel, 客户端停止画)
```

**客户端必须"合并"而不是"替换"**（`Store._merge_into`）—— 否则不推的字段会被清空。
这是"按需推"能成立的前提。

### 防丢帧：客户端自己收尾

帧可能被丢（慢客户端丢帧而非断线）。为避免"到站帧被丢 → 幽灵圆点永远在走"：

```gdscript
# entity_layer.gd
return float(Store.tick) < Protocol.num(tv.get("arrive"))   # 到站即不再画
```

### 2.3 限流：单帧字节数不能随模拟速度增长

实测（108 人，60Hz，盯 60 人的楼）：

| | 平均/帧 | 带宽 | **最大帧** |
|---|---|---|---|
| 改前 1x | 8.4 KB | 502 KB/s | 8.4 KB |
| 改前 1000x | 5.8 KB | 521 KB/s | 37 KB |
| 改前 1000x + 盯 60 人 | 26.8 KB | **2414 KB/s** | **136 KB** |
| **改后 1x** | **0.2 KB** | **13 KB/s** | 0.2 KB |
| **改后 1000x** | **0.3 KB** | **17 KB/s** | 9.9 KB |
| **改后 1000x + 盯 60 人** | **4.3 KB** | **257 KB/s** | **19 KB** |

五条控制：

1. **静态段只推一次**（物品 ~8 KB → 0）：物品带脏签名，变了才推。
2. **详情只给一个**（内存/事件不再随人数×时间膨胀）：只有选中的人带。
3. **观察集轮转**：N 人拆成多批、每帧一批 → 单帧有上限，
   每个人 ~`60/ceil(N/watch_pframe)` 次/秒刷新（盯 60 人 → 约 20Hz），
   进度条看起来仍是连续的。
4. **观察集粒度 = 当前页真正在看的东西**：
   - NPC 页 → **只报那一个人**（不要把整栋楼拖进来）
   - 建筑页 → **只报当前那一层**（`bld_x_fN`），不是整栋
   - 物件页 → 不报任何人

   同一栋 6 层 ×10 人的楼：报整栋 = 60 人（~240 KB/s），
   报一层 = 10 人（~70 KB/s）。
5. **详情降到 10Hz**：`rich_every = 6`（60/6）—— Inspector 自己就是
   `UiPage.bind` ~100ms 刷新的，60Hz 重发详情只是白烧。
   不推的帧靠客户端 merge 保留上次值。

### 实测（看一个人的状态）

```text
看一个人          0.49 KB/帧  ≈  29 KB/s   （改前 ~300 KB/s）
看某栋某一层      1.16 KB/帧  ≈  70 KB/s
看整栋(旧行为)    4.04 KB/帧  ≈ 242 KB/s
什么都不看        0.29 KB/帧  ≈  17 KB/s
```

### 实测效果（108 人）

```text
60Hz 平均   6.4 KB/帧  ≈  514 KB/s    （没看任何东西）
          21.3 KB/帧  ≈ 1703 KB/s    （盯着 60 人的楼：观察集 60 人全量）
原来全量    8.5 MB/s                 （108 人 × 全字段 × 60Hz）
静止时      一帧 0 个 NPC
出发/到站   只推那一个人；途中一帧不推
观察集      选中的 + 选中建筑里的人, 每帧都在（进度条才会动）
```

> 前端 HUD 右侧显示 `↓ x/s · ↑ x/s`（WS 载荷字节/秒），可直接看推送量是否健康。

## 5. 铁律

1. **不推 ≠ 不模拟。** 服务端永远照常演化全世界，只是不发。
2. **快照是全量状态，允许丢帧。** 丢了下一帧会补齐（`_pushed_tick` + 签名兜底）。
3. **客户端只合并，不替换。**
4. **选中变化才上报**（视图偏好，不是 simulation，不参与任何计算）。
5. 这条和定死的 **P8** 是一件事的两面：
   - **P8（写侧）**：玩家的手碰不到 NPC 的脑子
   - **观察驱动（读侧）**：客户端只收到它正在看的东西
   - 读侧收窄，**写侧没变** → 玩家的经营动作照样影响整座城市，只是他看不到看不见的地方。
