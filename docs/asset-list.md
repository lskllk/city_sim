# 资产定义（Asset Bible）

> **这份文档定义"这个游戏有哪些资产"，不定义"怎么生成"。**
> 代码是实现的一种，随时可以改/换；这份清单是规格。
>
> 上游：[游戏构思](game-concept.md)（玩法是什么）· [美术方向](art-direction.md)（画风）
> 实现现状：`art/`（生成器）· 本文 §九 有"现在有什么 / 缺什么"的对照
>
> 状态：**头脑风暴稿** —— 分类和判据先定，数量待定，欢迎推翻。

---

## 〇、先纠正一个前提

我前面做的事是「看到原型里有什么，就照着生成什么」。那是**执行**，不是**定义**。

标准做法应该反过来：**先从玩法推出"玩家会看到什么"，再按资产类别定义，最后才谈实现。**

而且分类的判据**不是外观，是玩法属性**。同样是"一个方块"：

| 长得像 | 但它是 | 因为 |
|---|---|---|
| 苹果、梨、面包 | **货** | 有存量、会消耗、会卖光、有保质期 |
| 床、马桶、工位 | **家具** | 恒为 1、永不消耗、一次一人用 |
| 货架、货箱、冰柜 | **容器** | 自己不消耗，装别的资产 |
| 收银台、销售台 | **工位** | 是"岗位"，必须有人站着才生效 |

**外观分不出这四类**（货架和冰箱都是长方形）。所以资产清单必须按**玩法属性**分。

## 〇·一、清单里带类别，预览按类别组织

`art/out/manifest.json` 的每个资产都带 **`cat`（九大类）+ `sub`（子类）** 两个字段，
由 `art/gen.mjs` 的 `categorize()` 统一判定（判据就是 §二 那张表）。

`wiki/out/art.html` 按这两个字段组织成一个**分类预览**，并且
**每个子类都标了"还缺什么"（虚线框）** —— 所以那张表同时是**缺口报告**。

当前的类别分布：

```
A 环境 22 · B 建筑 49 · C 角色 128 · D 物件 42 · E 界面 9 · F 特效 4 · G 氛围 2 · H 认知 0
                                                        ↑ 认知表现是最缺的
```

## 一、从玩法推出"玩家看得见什么"

游戏一句话：**一个视野有限的人，在一座小城里，靠关系和情报做买卖。**

玩家一天里在看什么、做什么：

```
看地图上的人和建筑        → 需要：环境 · 建筑 · 角色
走（自己控制的人）        → 需要：角色动画 · 寻路表现
进店/进屋                 → 需要：室内结构 · 屋顶淡出
点货架/家具               → 需要：可交互物件（货/家具/容器/工位）
卖东西（顾客→柜台→成交）   → 需要：交易表现 · 气泡 · 工位状态
看面板（笔记本/账本/关系）  → 需要：界面 · 图标 · 头像 · 图表
快进（时间流逝）           → 需要：特效 · 氛围 · 结束摘要
昼夜、天气                → 需要：氛围与光照
感受"我知道的是旧的"       → 需要：★ 认知表现（这个游戏特有）
```

八条里最后一条最特殊 —— **没有别的游戏需要它**。所以它必须是独立的一类资产，不能塞进 UI 图标里。

## 二、九大类别（总表）

| # | 类别 | 前缀 | 定义判据 | 交付单位 | 估算 |
|---|---|---|---|---|---|
| **A** | **环境** | `env_` | 铺在地面/地面的东西，不参与交互 | tileset + 散件 | ~90 |
| **B** | **建筑** | `bld_` | 有门口、能走进去、有识别名 | 每栋一套分层 | ~60 |
| **C** | **角色** | `chr_` | 会走动、有需求、有记忆 | 部件 + 图集 | ~500 |
| **D** | **可交互物件** | `itm_` | **玩家能点、能买卖、能用** | 单件（俯视 + 图标） | ~130 |
| **E** | **界面** | `ui_` | 屏幕空间的：图标 / 装饰 / 图表 | 图标集 + 九宫格 | ~90 |

| **I** | **数据与配置** | — | 图集清单 / 调色板 / 动画定义 / 九宫格 | JSON | — |

## 三、逐类定义

### A. 环境 `env_`

**判据**：铺在地上、或立在地上但**不参与交互**。

**为什么单独一类**：它占地表面积最大，但玩法上完全不重要 —— 所以它应该**便宜、可平铺、可复用**，不用精雕。

| 子类 | 内容 | 交付单位 |
|---|---|---|
| **A1 地面** | 草地×3 · 泥土×2 · 广场砖×2 · 水×3 · 碎石×1 · **室内地板×4**（木/瓷砖/水泥/地毯） | 32px 可平铺 tile |
| **A2 道路** | 沥青 · 人行道 · 路缘石×2 · 标线×4 · 斑马线×2 · 路口铺装×3（十字/T/尽头）· 井盖 · 排水沟 | 32px tile |
| **A3 过渡与拼接** ★ | 草↔泥 ×8 · 草↔水 ×8 · 铺装↔草 ×8 · 路肩 ×4 | **autotile 集** |
| **A4 地块装饰** | 树×5 · 灌木×3 · 花丛×3 · 石头×3 · 杂草×2 · 水井 · 邮筒 · 垃圾桶×2 · 长椅×2 · 路灯×2（开/关）· 电线杆 · 自行车×2 · 摊位车×2 · 遮阳伞×2 · 公告栏 · 花坛×2 | 散件（底部锚点） |
| **A5 围栏与院子** | 木栅栏 · 矮砖墙 · 树篱 —— 各 4 段（直/角/端/门） | 散件 |

> ★ **A3 是"业余 vs 专业"最大的分水岭。**
> 只有 A1 没有 A3 的地图，到处是硬边 —— 一眼就是新手做的。
> 标准做法是 **autotile（47-tile blob 或 16-tile 简化集）**，不是一张张画。

---

### B. 建筑 `bld_`

**判据**：有门口、能走进去、有名字。

| 子类 | 内容 | 交付单位 |
|---|---|---|
| **B1 建筑本体** | 按 `config/buildings/` 的 12 种，每种 2~3 个外观变体 | 每栋一张（屋顶+立面+门口） |
| **B2 分层** ★ | `_body` / `_shadow` / `_lit`（夜光）三张 | 每栋三张 |
| **B3 附件（可复用）** | 招牌底×6（木板/铁皮/霓虹/布幡/灯箱/手写）· 雨棚×3 · 烟囱×2 · 空调外机×2 · 水箱 · 台阶×2 | 可挂在任意建筑上 |
| **B4 状态** | 关门挂牌×2（休息中/打烊）· 装修中（脚手架/围挡）×2 · 出售/出租牌×2 | 叠加层 |
| **B5 室内结构** | 室内墙×2 · 室内门×3（开/关/推拉）· 室内窗×2 · 楼梯×2 | 散件 |

**两条纪律**：
```
① 招牌的【字】不进贴图 —— 招牌底是资产，字是代码画的（编辑器能改名）
② 建筑本体必须分层：body / shadow / lit 分开，因为落影要能被夜/雨复用、
   夜光要能被"天黑"单独点亮
```

### C. 角色 `chr_`

**判据**：会走动、有需求、有记忆。

**★ 核心原则：部件化，不是每人一套。**

```
不做的：40 个人 × 3 方向 × 5 帧 = 600 张（而且第 41 个人就得再画一套）
要做的：部件库 × 组合
```

| 子类 | 内容 | 数量 |
|---|---|---|
| **C1 身体** | 瘦 / 中 / 胖 | 3 |
| **C2 头发** | 短发 / 长发 / 白发 / 帽子 / 秃 / 发髻 | 6 |
| **C3 上衣** | 衬衫×2 / 毛衣 / 外套 / 围裙 / 工作服 / 连衣裙 / 背心 | 8 |
| **C4 下装** | 长裤 / 裙 / 工装裤 | 3 |
| **C5 配饰** | 眼镜 / 拐杖 / 挎包 / 菜篮 / 工具包 / 伞 / 围巾 / 耳机 | 8 |
| **C6 职业道具** | 工牌 / 医生袍 / 工人帽 / 店员围裙 / 学生书包 | 5 |
| **C7 动画** | 走×4 · 站×1 · **待机小动作×2**（换重心/看表）· 坐×2 · 用东西×3（吃/睡/如厕） | 12 组 |
| **C8 头像** | 面板用的胸像 | 每人 1（或分层生成） |

**组合数**：3 × 6 × 8 × 3 × 8 = **3456 种人**。40 人小镇绰绰有余。

> ⚠ **C7 的"待机小动作"值不值**：NPC 站着不动像木头，加一个"换个重心"的 2 帧，
> **整个人就活了**。这个性价比比多画 10 种衣服高得多。

---

### D. 可交互物件 `itm_` ★ 你最关心的这一类

**判据**：**玩家能点它、能买卖它、能用它。** —— 这一条把 D 类和 A4（地块装饰）彻底分开。

**四小类的判据（按玩法属性，不按外观）**：

| 子类 | 判据 | 例子 | 状态 |
|---|---|---|---|
| **D1 货** `goods` | 有存量、会消耗、有保质期、会卖光 | 苹果 · 梨 · 面包 · 牛奶 · 简餐 | **满 / 半 / 空** |
| **D2 原料** `material` | 工厂产出、批发市场收、不能吃 | 简餐原料 · 面粉 · 包装盒 | 满 / 空 |
| **D3 家具** `fixture` | 恒为 1、永不消耗、一次一人 | 床 · 马桶 · 餐桌 · 衣柜 · 沙发 | 空 / 占用 |
| **D4 工位/设备** `station` | 是"岗位"，**必须有人站着才生效** | 销售台 · 工位 · 工业机器 | 无人 / 有人 |
| **D5 容器** | 自己不消耗，**装别的资产** | 货架 · 货箱 · 冰柜 · 展示柜 | 空 / 半 / 满 |

**★ D5 容器是独立一类，这是关键结构决定。**

```
错的做法：苹果货架 = 一个"苹果货架"贴图
对的做法：货架（容器） + 苹果（内容） 两个资产叠加

为什么：
  · 同一个货架要能放苹果、梨、面包（换内容不换容器）
  · "卖光了" = 容器还在、内容没了（不用画一张新贴图）
  · 库存数量可以叠 1~3 层小图标
```

**清单**：

| 子类 | 内容 | 数量 |
|---|---|---|
| D1 货 | 见 [物品设计](item-catalog.md)（65 件，按玩法作用分十类） | 按件 × (世界 + 空态 + 图标) |
| D2 原料 | 简餐原料 / 面粉 / 包装盒 / 水果原料 | 4 × 2 态 = 8 |
| D3 家具 | 睡眠 4 · 卫生 4 · 饮食 8 · 存储 5 · 装饰 6 | ~27 |
| D4 工位 | 销售台×2 · 工位×2 · 机器×3（等级）· 收银机 | 8 |
| D5 容器 | 货架×4（长/短/壁挂/端头）· 货箱×2 · 冰柜 · 展示柜 | 8 |
| 图标 | 每件的 16×16 正视图标（给面板用） | 按需 |

**每个物件交付两套"语言"**（这是上一轮已经确认的判决）：

```
世界形态 = 俯视   （地图是俯视的，摆在地上要贴地）
图标形态 = 正视   （16px 小图标，正视才认得出来 —— 俯视的苹果就是个圆）
```

### E. 界面 `ui_`

**判据**：屏幕空间的，不随地图缩放。

| 子类 | 内容 | 数量 |
|---|---|---|
| **E1 图标系统** ★ | 一套线性图标（1.5px 描边 / 24 网格）：时间类5 · 经济类4 · 需求类5 · 社交类5 · 功能类7 · 地图类4 | ~30 |
| **E2 物品图标** | D 类每件的 16×16 | ~60 |
| **E3 面板装饰** | 纸底×3 · 边框（**九宫格**）×4 · 分隔线×3 · 角标/标签×4 | ~14 |
| **E4 图表元件** | 进度条（九宫格）×3 · 区间条底/填充×4 · 柱/折线/刻度×5 | ~12 |
| **E5 光标与交互态** | 默认/可点/拖动/禁止 ×4 · 选中环×2 · 悬停高亮×2 | ~8 |

> ★ **E1 必须是"一套"，不是拼出来的。**
> 我现在的原型里混了三种：emoji（⚙▣▤◧）+ 手写 SVG + 纯字符（●❞∿）。
> 这是"不专业"最直观的来源。**统一描边粗细、统一网格、统一 currentColor。**

### F. 特效 `fx_`

**判据**：一次性、短命、不占位置。

```
落影 ×3（小/中/大）· 选中环 ×2 · 点击涟漪 ×3 · 完成打勾 ×2
路径点/虚线 ×2 · 气泡底/尾 ×2 · 交易成功 ×2 · 惊讶闪现 ×2
```
≈ 20

---

### G. 氛围 `atm_`

**判据**：覆盖全屏、影响整体观感、不改变任何逻辑。

```
时间色调 ×5（清晨/白天/黄昏/夜/深夜）  ← 现在只有一个"夜色 multiply"
窗光遮罩 ×2 · 灯光光斑 ×3
雨 ×2（小雨/大雨）· 雪 ×2 · 落叶/飞虫 ×2 · 雾 ×1
```
≈ 17

> 这一类比看起来重要得多：**同样的地图，黄昏和正午是两个游戏。**
> 现在的实现只有一个 `#0d2340 × 0.55` 的乘法层 —— 那是占位，不是氛围。

---

### H. 认知表现 `cog_` ★ 这个游戏特有

**判据**：**表达"我记的有多旧 / 有多准 / 从哪来"。没有别的游戏需要这一类。**

| 子类 | 内容 | 现在 |
|---|---|---|
| **H1 来源记号** | 亲眼 / 打听 / 传闻 / 雇员 / 经手 | 字符 `●❞∿◐▮`（要重做） |
| **H2 精度档记号** | 5 档的视觉（**区间条**的底/填充/端帽） | 代码画的 div |
| **H3 知识等级** | 3 档（没去过 / 旧了 / 新鲜） | `filter: saturate()` |
| **H4 状态反馈** | 惊讶 / 刚确认 / 已过时 / 待确认 | 部分有 |
| **H5 关系可视化** | 好感度 / 熟客程度 / "谁跟谁说过话"的连线 | 只有数字 |

**这一类要单独讨论一个设计问题**：

```
它是【资产】还是【规则】？
  · 如果是资产（一组贴图）→ 优点是美术可调，缺点是"衰减曲线变了要重画一套"
  · 如果是规则（代码 + 参数）→ 优点是改一处全局生效，缺点是美术插不上手

我的建议：**混合**。
  · 形状/记号 = 资产（H1 的记号、H3 的三档底图、H2 的条）
  · 强度/阈值/颜色映射 = 规则（在 config 里，不在贴图里）
```

### I. 数据与配置

不是美术，但属于"资产"，且**标准化最容易被忽略的地方**：

```
· 图集（atlas）：把散图打成一两张，附 JSON。★ 现在是一张张散文件（195 个 = 195 次请求）
· 调色板文件：色板的唯一真源（现在在 style.json 里，只有生成器读）
· 动画定义：帧序 / 帧率 / 循环（现在是靠文件名猜 walk0..3）
· 九宫格定义：哪些 UI 可以拉伸、拉伸区在哪
· 图层清单：哪张图属于哪一层（现在在 manifest 的 layer 字段里）
```

## 四、命名规范（标准化）

现在命名是随手的（`tree_m` / `shop_a` / `n_wang_down_walk0`）。标准做法：

```
{类别}_{子类}_{名字}_{变体}_{状态}

env_ground_grass_a            环境 · 地面 · 草 · 变体a
env_road_corner_ne            环境 · 道路 · 转角 · 朝东北
env_prop_tree_a_large         环境 · 装饰 · 树a · 大
bld_shop_a_body               建筑 · 店 · 变体a · 本体
bld_shop_a_lit                建筑 · 店 · 变体a · 夜光
bld_attach_sign_wood          建筑 · 附件 · 招牌 · 木板
chr_body_slim_down_walk0      角色 · 身体 · 瘦 · 下 · 走0
chr_hair_short_down_walk0     角色 · 头发 · 短 · 下 · 走0
itm_goods_apple_full          物品 · 货 · 苹果 · 满
itm_goods_apple_empty         物品 · 货 · 苹果 · 空
itm_fixture_bed_single        物品 · 家具 · 床 · 单人
itm_station_counter_a         物品 · 工位 · 销售台 · 变体a
itm_container_shelf_long      物品 · 容器 · 货架 · 长
ui_icon_need_hunger           界面 · 图标 · 需求 · 饿
ui_icon_source_eyewitness     界面 · 图标 · 来源 · 亲眼
fx_shadow_m                   特效 · 落影 · 中
atm_time_dusk                 氛围 · 时间 · 黄昏
cog_precision_lv3             认知 · 精度 · 第3档
```

**四条规则**：
```
① 前缀定类别（env/bld/chr/itm/ui/fx/atm/cog）—— 一个文件是什么，一眼看得出
② 全小写 + 下划线，不用驼峰、不用连字符、不用空格
③ 变体用 a/b/c，状态用词（full/empty/open/busy）—— 不要用数字当状态
④ 序号从 0 开始（walk0..walk3），因为程序里是数组下标
```

## 五、交付规范

| 项 | 规格 |
|---|---|
| **网格** | 1 格 = 32px（逻辑）。所有地图件必须对齐 |
| **绘制倍率** | 2× 绘制、2× 声明（相机上限 2.4×，超了会糊） |
| **锚点** | `topleft` 地图件 · `bottomcenter` 立在地上的 · `center` 标记与俯视物件 |
| **图集** | 按类别打包（env / bld / chr / itm / ui / fx），附 JSON |
| **九宫格** | 所有可缩放的 UI（面板、按钮、进度条）必须给拉伸区定义 |
| **动画** | 给帧序 + 帧率 + 是否循环，不要让程序猜文件名 |
| **状态** | 用变体表达（`_empty` / `_lit` / `_open`），**不要做成不同资产** |
| **文字** | 一律不进贴图（招牌、标签、数字都是代码画的） |

## 六、优先级（分四层，从"能证明玩法"倒推）

```

## 七、这份清单里"非标准"的四个决定（要拍）

大部分项目不会有这四条，但**这个游戏需要**：

| # | 决定 | 为什么 |
|---|---|---|
| 1 | **认知表现独立成一大类（H）** | 玩法核心是"我知道的是旧的"，它不是 UI 的一部分，是**主角** |
| 2 | **容器与内容分离（D5）** | 货架 × 货 是两个资产。"卖光了" = 容器还在、内容没了 |
| 3 | **物件按玩法属性分四类**（货/家具/工位/容器），不按外观 | 外观分不出，玩法分得出 |
| 4 | **招牌的字不进贴图** | 编辑器能改建筑名，写进贴图就死了 |

### 原来的问题（存档）

```
① 小人从"俯视"还是"斜俯视"画？
   现在是一致的正俯视（看不见脸）。斜 30° 会人性化得多，但所有资产要重画。
   而且它跟"2D↔2.5D 可逆"那句决定冲突吗？（决定 #5）

② 室内怎么做？
   现在：屋顶淡出 → 看到地板和家具（正俯视的"平面图"感）
   另一种：进屋后切到一个单独的室内场景（更有空间感，但要多一套资产 + 多一层关卡）

③ 货的"数量"怎么表现？
   一个图标叠 1~3 层？一个数字？一条小刻度？—— 这决定 D1 要出几套状态

④ 建筑要不要"能看到内部"（俯视看进屋里）还是只看到屋顶？
   现在：只看到屋顶，走进去才淡出

⑤ 天气要做到什么程度？
   只做色调 + 雨（便宜）？还是雪/雾/落叶（贵，且要重画地面）

⑥ 头像（C8）做不做？
   做了，面板里"认出人"会强很多；不做，就继续用小尺寸的小人剪影
