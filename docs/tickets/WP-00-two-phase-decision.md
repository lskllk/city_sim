# WP-00 拍板：两阶段 vs 顺序执行

- 状态：done
- 阶段：—（决策票）
- 依赖：无
- 阻塞：WP-06、WP-15
- 大小：S

## 背景

现在 `engine.tick` 是**两阶段**：

```python
for npc_id in due: decisions.append(npc.process(...))   # ① 同一帧快照决策
for ...: _apply(...)                                     # ② 统一执行
```

注释写明用意：**所有人基于同一帧世界决策**，结果与先后无关。

端口化后 NPC 在自己这一轮直接 `port.try_take(...)` 会改世界。于是：

- 先跑的 NPC 拿走最后一张床 → 后跑的看到的是**已经变过的世界** → 顺序依赖。

## 两个选项

**A. 保留两阶段（提交相）**
- `try_*` 在决策相不能立即改账，只能记“请求”，提交相统一落。
- 代价：`Ack/Deny` 异步 → NPC 自处理失败打折；要加 commit 队列；顶层还在但变瘦。
- 保住公平性（无先手优势）。

**B. 顺序执行（推荐）**
- `due_npcs()` 已经 `sorted(world.npcs)`，按固定 id 顺序立即改世界 → **确定性/回放仍成立**。
- 代价：**公平性变化**（id 靠前的先抢到）。
- 简单，真正拉到“NPC 主动”。

**C（混合）**：只有**争用资源**（床/台/店队）保留提交相，其余立即。

## 验收

- 在票里写下选择与理由（改本文件「决定」段）。
- 若选 B：确认 `test_replay.py` 在同 seed 下仍逐 tick 一致。
- 若选 A/C：给出 commit 队列的数据结构与失败回传约定。

## 决定

**选 B：顺序执行。** 理由：

- `due_npcs()` 返回 `sorted(world.npcs)`，固定 id 顺序 → 确定性/回放仍成立
  （`test_replay.py` 兜底）。
- 端口化后 `observe → decide → try_*` 在**同一个人的同一轮**里完成，天然没有
  TOCTOU（决策与执行之间世界不会变），比两阶段更简单。
- 代价：公平性变化（id 靠前的先抢到争用资源）。可回放、可接受。
- 不做 commit 队列（A/C 的复杂度留到真需要时再上）。

**影响**：`engine.tick` 的 5b 从「先全员 Decision，再统一 `_apply`」变成
「`for pid in due: npc.step(port, cfg, can_preempt)`」。WP-06 按此实现。

回滚：若后续发现公平性不可接受，改为 A/C 只影响 `engine.tick` 的 5b 循环 + 端口
的提交方式，端口契约（WP-01）不变。

## 风险

公平性变化会影响 `test_multi_use`（3 张床 3 人）等，需确认“谁先”是否可接受。
